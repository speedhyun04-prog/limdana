## 결정 사항

- 설계 단일 출처: `docs/ARCHITECTURE_ROOMS_GROUP.md` (G1 단체방 / G2 파일 / G3 방 공지 /
  G4 방 일정 / G5 방 봇). 각 단계 완료 시 그 문서에 "구현 기록" 절을 덧붙인다.
- **어댑터 원칙**: 단체방도 서버가 `peer` 자리에 표시용 객체(name=방 이름, dept="n명",
  group=true)를 채워 내려준다. `peer` 전제가 14개 파일 95곳이라 전면 리팩터 대신
  회귀 면적을 줄이는 쪽을 택했다. msn.js·search.js·notify.js 는 무변경 유지가 목표이고,
  거기에 변경이 생기면 어댑터 설계가 깨진 신호.
- 1:1 방에서 초대하면 **기존 방을 승격하지 않고 새 단체방**을 만든다(카톡과 동일).
  pair 방 id 가 uid 쌍의 결정적 해시라, 승격하면 그 상대를 다시 열 때 남이 낀 방이 열린다.
- 단체방 id 는 `g`+uuid(11) — 1:1 해시는 hex 뿐이라 충돌 불가. `kind` 없는 레코드는
  direct 로 읽는다(구버전 방 무변환, 일괄 마이그레이션 없음).
- 초대된 사람은 `joins{uid: 메시지개수}` 기준으로 이전 대화를 못 본다. 시스템 메시지
  (입장·퇴장·이름 변경·공지 등록)는 안읽음 배지에서 제외.
- 파일은 이미지(`/files/`)와 저장소를 분리. 원본 확장자로 저장하지 않고 `uuid.bin`,
  원본 이름은 메타 json 에만. 실행형 확장자 업로드 거부, 20MB. 전송은 `{file:"<id>"}`
  만 받고 이름·크기는 서버 메타가 단일 출처(표시 위조 차단).
- 다운로드는 `/roomfile/{id}` — `/api/*` 는 원격 무토큰을 미들웨어가 401 로 막는데
  `<a download>` 는 헤더를 못 싣는다. 이미지 `/files/` 와 같은 예외 처리(원격은 `?t=`).
- 방 공지는 방 레코드 안 한 건(`notice`)만. 전사 게시판은 그룹웨어 몫(§9.3).
  본문을 복사해 저장하므로 원본 메시지를 지워도 공지는 남는다.
- G4 방 일정은 새 백엔드를 만들지 않고 그룹웨어 `events`(2단계 §9.2)에 room 스코프로
  흡수한다 → **그룹웨어 §9.2 구현이 선행**. 그전까지 서랍에 항목을 만들지 않는다.
- G5 방 봇은 `@아호비` 호출 전용, 봇 명의 발화라 "AI는 초안, 발신은 사람" 위배 아님.
  도구 없음·방 밖 행동 없음, 호출자 클로드 키로 과금. 비용 판단 필요해 보스 승인 대기.
